方向是对的，基础层是坏的

这个扩展的产品判断很准——把一次 400 毫秒内的裁决做成悬浮层，信息模型（相关度/新信息/可信度/时效性 → 三档结论）也是扎实的。 问题全部不在「想得对不对」，而在视觉系统与显隐机制没有被建立起来：颜色账本是混的、[hidden] 是失效的、 快捷键是双触发的、搜索结果徽章在真实页面上是不可读的。下面每一条都附了实测数字。

先看硬门槛。分数本身不重要——只要有任何一条硬门槛失败，结论就是不放行。 本次失败两条：① 文字对比度（搜索结果四档徽章在浅色页上实测 1.55–4.17:1，全部低于 4.5:1； 其中三个等级色低于 2.3:1，等同于不可读）；② 键盘焦点（全局没有任何 :focus-visible 样式， 纯键盘用户看不到自己在哪里）。

再看分数为什么这么低。不是审美不够，是系统缺失。三个最贵的症状： 所有依赖 hidden 属性的显隐全部失效（4 个容器漏出，结果卡顶部会永久挂着一行「正在读取当前页面…」）； 同一套判定色同时承担「结论等级」和「数值高低」两种语义，导致色彩无法被信任； Alt+Shift+R 被内容脚本和浏览器命令各触发一次，净效果等于快捷键没反应。

但有一个维度做得明显好：内容与反馈。错误分类（404/401/422/429/529）、退避重试、本地估算与模型结果的诚实标注、 每种「不弹浮层」的原因都会告诉用户为什么——这套文案逻辑比绝大多数同类扩展考究。重构时应原样保留。

逐条发现

点击任一条展开证据与修正

P0 所有依赖 hidden 属性的显隐全部失效 弹窗打开时，结果卡上会永久挂着一行「正在读取当前页面…」，以及一条孤立的 1px 分隔线 ›
现象UA 样式表里的 [hidden]{display:none} 优先级低于作者样式。而 .loading / .verdictwrap / .metrics / .chips / .metaline 五个类都声明了 display，于是把 hidden 整个抵消掉。
影响加载态永远不会消失（$("loading").hidden = true 无效）；初次打开时会出现一个空圆环 + 孤立的「—」；空的 .metaline 会渲染一条 border-top 横线；三个空 flex 容器额外占掉约 33px 高度。用户第一眼看到的是一个坏掉的界面。
证据用项目自带的 jsdom 加载真实 popup.html + popup.css 后逐元素取 computed style：
id hidden属性 computed display verdictwrap true flex ← 应为 none metrics true flex ← 应为 none chips true flex ← 应为 none metaline true flex ← 应为 none unsupported true none ← 该类没有声明 display，所以正常
修正加一行兜底即可，同时覆盖未来新增的元素：
/* 三个页面的 reset 区域各加一行 */ [hidden] { display: none !important; }
复测重跑 jsdom 脚本，五个 id 的 computed display 应全部为 none（loading 在初始态为 flex）；再在浏览器里打开弹窗，确认加载行在结果渲染后消失、结果卡顶部无孤立分隔线。
P0 搜索结果徽章在浅色页面上不可读 四档等级色 1.55–4.17:1，全部低于 4.5:1；等级只靠色相区分 ›
现象serp.js 把所有颜色写在行内样式里，直接复用深色 UI 的 VERDICT[*].color 作为 11px 文字色。亮绿、亮琥珀在白色背景上不可能达标。
影响搜索结果标注是这个扩展的第二大功能，但在真实浅色结果页上等级几乎看不清；若宿主页是暗色模式，#64748B 文字与 #333155 汇总条会跌到 2.55:1 和 1.32:1——完全不可读。等级区分只有色相，灰度/色觉障碍下失去全部信息。
证据WCAG 2.1 对比度计算（b.contrast_audit.py）：
浅色宿主页 read #34D399 on #E3F9F1 1.75:1 需 4.5 skim #FBBF24 on #FEF6E0 1.55:1 需 4.5 skip #94A3B8 on #F0F2F5 2.29:1 需 4.5 pending #64748B on #EEF0F4 4.17:1 需 4.5 深色宿主页 pending #64748B on #33363C 2.55:1 汇总条 #334155 on #262E39 1.32:1
修正 ① 反转编码为浅底深字（read #065F46 on #D1FAE5，skim #78350F on #FEF3C7，skip #334155 on #E2E8F0，pending #475569 on #EEF1F5）； ② 用容器背景亮度选明暗套——读一次 getComputedStyle(container).backgroundColor，相对亮度 > 0.5 用浅色套，否则深色套； ③ 每档加非颜色线索（实心点 / 空心底 / 短横），并保留文字标签；
④ 字号 11→12px，圆角 6→4px；
⑤ 顺手把行内样式搬进 style 节点，用 CSS 变量主题化。
复测在 Google（浅色 + 暗色）、Bing、百度各跑一次，用取色器抽查四种徽章的前景/背景对，确认 ≥4.5:1；截图后转灰度，确认四档在灰度下仍可分。
P1 快捷键 Alt+Shift+R 被触发两次，净效果等于没反应 内容脚本和浏览器命令各处理一次，toggle 两次回到原点 ›
现象hud.js 在 document 上监听 Alt+Shift+R 并调用 toggle()；同时 manifest.json 声明了 commands.toggle-panel，service-worker.js 收到后也发 RS_TOGGLE_PANEL 给同一个内容脚本。两条路径各 toggle 一次。
影响用户按快捷键后浮层闪一下又回到原状，只能判断为「快捷键坏了」。这是文档里宣传的核心操作之一。
证据src/content/hud.js 第 723–729 行与 src/background/service-worker.js 第 302–311 行，两处对同一组合键各自独立处理。
修正删掉 hud.js 里的全局 keydown 分支，只保留 chrome.runtime.onMessage 的 RS_TOGGLE_PANEL 分支——快捷键由浏览器统一路由，页面脚本不应抢。同时把 Escape 也改成有条件的：只有焦点在浮层内部、或指针悬停于浮层时才响应，并 stopPropagation，避免吃掉宿主页自己的 Esc 行为。
复测按一次 Alt+Shift+R，浮层状态应翻转一次；在带 Esc 快捷键的站点（如 GitHub issue 编辑）按 Esc，宿主页行为正常，浮层不响应。
P1 色彩账本混乱：同一套颜色同时是「结论等级」和「数值高低」 绿既是「值得读」又是「数值高」，灰既是「可跳过」又是「数值低」 ›
现象VERDICT.read/skim/skip 用绿/琥珀/灰；chip.hi/mid/lo 又用绿/琥珀/灰；指标条的填充色还跟着判定色走；chip.mid 与 chip.warn 的定义完全相同，属于冗余变体。一个卡片上最多同时出现 6 种色相（判定色 ×2 渐变端点、accent、hi、mid、lo）。
影响同一颜色在不同位置含义不同，用户无法建立「绿=什么」的稳定认知。当「阅读价值 高」和「可信度 低」同时出现时，同一个绿色既是好消息又是坏消息，颜色失去可被信任的语义。
证据对比 src/lib/constants.js 的 RS.VERDICT（#34D399 / #FBBF24 / #94A3B8）与 hud.js 的 .chip.hi/.mid/.lo（#6EE7B7 / #FCD34D / #A9B4C4）与 popup.js 的 tone 映射——三处是同一套色相做三种语义。
修正建立角色表并强制执行：判定三色只用于结论（判定词、顶部综合分条、角标圆点）；数值一律用判定色单一色相，不按高低换色；chip 全部中性（文字色 + 细描边），只有警告类才允许琥珀。删掉 chip.mid。
复测把卡片截图转灰度：判定词仍应是画面中对比最强的一处；随机抽 5 个页面，确认不存在「一个色相两种含义」的组合。
P1 视觉层级与任务优先级不匹配：圆环抢走了判定词的位置 52×52 的渐变圆环是画面的第一视觉，而产品的价值在「值得认真读」这五个字 ›
现象圆环占 52×52、带渐变描边、内部放 14px 粗体数字；判定词只有 16px。同一个信息被表达了三次（环的填充长度、环的颜色、环内的数字）。卡片上另外还有 6 条边界线索在争夺注意力。
影响模糊或灰度下，第一眼看到的是一个百分比，而不是「读 / 扫 / 跳」这个可执行的结论。判定词是用户唯一需要的东西，却被降为第二层级。
证据模糊测试：将现状卡片高斯模糊 6px，判读顺序为「圆环 → 彩色 chip → 判定词」。第一视觉与任务目标不一致。
修正删除圆环。判定词升到 20px/600 成为唯一第一视觉；综合分降为标题行右端的 13px 等宽数字；把原来那条纯装饰的顶部 2px 渐变光条改造成真实的综合分刻度——同一像素位同时完成去装饰和加信息。边界线索从 6 条收到 3 条（不透明填充 / 1px 边框 / 一个外投影）。
复测同样做 6px 模糊测试，判读顺序应为「判定词 → 4 根细条 → 数字」；灰度测试下判定词仍是最强对比。
P1 中文小字普遍偏小，第三级文字色低于 4.5:1 10.5px 与 11px 中文共出现在 9 处；--dim 系列实测 3.75–4.43:1 ›
现象chip 10.5px、metaline 10.5px、footmeta 10.5px、rlabel small 10.5px、% 单位 9px、stats 11px、标签 11 / 11.5px。第三级文字色 #767e8d / #7a8291 / #7C8494 在各自背景上全部不足 4.5:1。同一指标的标签列宽在 popup 是 58px、在 HUD 是 62px。
影响中文笔画密度远高于拉丁字母，10.5px 在 Windows 默认渲染下会糊成一团（尤其「新信息程度」「阅读价值」）。低对比的第三级颜色又叠加在过小的字号上，等于双重削弱。

P1 可访问性缺失：无焦点样式、无 reduced-motion、命中区不足 纯键盘用户看不到焦点位置；三个页面都没有动效降级 ›

P1 9 秒自动收起会打断键盘用户，并可能在卡片被裁切时误定位 收起条件只检查 :hover；位置夹紧用的是硬编码高度 300px ›
现象expand() 的自动收起回调只判断 S.card.matches(":hover")。键盘用户把焦点移进卡片后，9 秒到点卡片照样收起，焦点被丢到 body。同时 applyPosition() 用 h = 300 这个估计值做边界夹紧，而卡片实际高度随警告条与 chip 数量变化（实测约 250–340px）。
影响键盘用户正在读卡时内容消失；在低矮窗口里卡片底部按钮可能被夹到视口之外，而它是唯一能点「重新评估」的地方。

06

修订顺序

按「先解阻塞、再解系统性成因」排序

  1. 加一行 [hidden]{display:none!important}（三个样式表）。一行代码解掉一个 P0，先把弹窗恢复成可用状态。
  2. 重写 SERP 徽章配色与明暗分流，并把行内样式搬进样式节点。这是第二个 P0，也是用户能直接看到的对比度问题。
  3. 删掉 hud.js 的全局 keydown 分支，只由 chrome.commands 路由；Escape 改为条件响应。
  4. 落地设计令牌（15 个变量）到三个页面，把 --dim 一级删掉、圆角与间距收敛到档位。这一步做完，后面所有组件改动都有依据。
  5. 重做 HUD 卡片：删圆环、顶部条改综合分、指标条改 2px 直角、chip 中性化、字号回到 12px 起。
  6. 补可访问性：焦点环、prefers-reduced-motion、44px 命中区、自动收起时保留焦点。
  7. 换图标：改 tools/make_icons.py 为单色底 + 三段刻度，重新生成四个尺寸，弹窗与设置页同步换用同一符号。
  8. 设置页补浅色主题：它是整页 tab，跟随 prefers-color-scheme，否则浅色系统用户会突然遇到一整页黑。

第 1–4 步做完，硬门槛即解除，分数会从 45 升到 70 上下；第 5–8 步是把「可用」变成「好」。
